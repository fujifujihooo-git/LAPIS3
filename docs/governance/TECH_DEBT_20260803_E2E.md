## TD-001: Firestore再接続遅延（22秒問題）

| 項目 | 内容 |
|---|---|
| **概要** | ページ遷移を繰り返すと、FirestoreのPhase 2データロードが通常253msに対し22,909ms（約90倍）に劣化する |
| **発見経緯** | Scenario B→C遷移時、`procedure_name` の値が10秒以内に設定されずタイムアウト。ログ確認で `[Perf] All Phase 2 data loaded in 22908.9ms` を検出 |
| **影響範囲** | `detail.html` を含む全Firestoreページ。特にWebChannel/Long Pollingを使うSPA系画面で発生リスクあり |
| **発生頻度** | テスト環境（エミュレータ）で確認。本番での発生は未確認 |
| **優先度** | **高（調査のみ）** |
| **推奨対応** | 本番環境で同様の遅延が発生するか計測。発生する場合、Firestore接続のライフサイクル管理（明示的disconnect/reconnect）を検討 |
| **概算工数** | 調査: 2時間 / 改修（必要な場合）: 4〜8時間 |
| **今回対応しなかった理由** | エミュレータ特有の可能性があり、本番影響が未確認。テスト側のタイムアウト拡大（10s→30s）で暫定対処済み |

## TD-002: テストデータ生成の標準化

| 項目 | 内容 |
|---|---|
| **概要** | E2Eテストのテストデータ生成が `test_acceptance_step1.js` 内にインラインで記述されており、再利用性・保守性が低い |
| **発見経緯** | テスト作成時に `estimateItems`（キャメルケース）で保存し、`detail.js` が `estimate_items`（スネークケース）を読む不一致が発生。テストデータ生成の仕様管理が不在だったため |
| **影響範囲** | 今後追加されるE2Eテスト全般。テストが増えるほど、データ生成の一貫性欠如が品質リスクになる |
| **発生頻度** | E2Eテスト追加のたびに発生リスクあり |
| **優先度** | **中** |
| **推奨対応** | `generate_test_data.js` にE2E用のテストデータ生成関数を集約。フィールド名はプロダクションコードと同一のスネークケースを使用。テストからは `require('./generate_test_data')` で呼び出す |
| **概算工数** | 4〜6時間 |
| **今回対応しなかった理由** | Step 1テスト通過を優先。インラインのデータ生成でも動作するため、機能的には問題なし |

## TD-003: staff生成ロジックの維持管理

| 項目 | 内容 |
|---|---|
| **概要** | `generate_test_data.js` でのstaff（スタッフ）ドキュメント生成と、Auth Emulatorのユーザー作成の整合性が脆い |
| **発見経緯** | 初期テスト実行時、`lapis-test` ユーザーに対応する `staff` コレクションのドキュメントが存在せず、`permission-denied` エラーが発生。Auth Emulator REST APIで直接確認し、staffドキュメントの手動投入で解決 |
| **影響範囲** | テスト環境のセットアップ。エミュレータをリセットするたびに再発リスクあり |
| **発生頻度** | エミュレータ再起動/データクリア時 |
| **優先度** | **中** |
| **推奨対応** | `generate_test_data.js` に「Authユーザー生成 → staff生成 → 顧客生成 → 案件生成」の順序保証を組み込む。冪等性を確保し、既存データがあればスキップする |
| **概算工数** | 2〜3時間 |
| **今回対応しなかった理由** | 今回のセッションで部分的に改善済み。残課題の整理が必要 |

## TD-004: 命名規約の不統一（camelCase / snake_case混在）

| 項目 | 内容 |
|---|---|
| **概要** | Firestoreのフィールド名に `camelCase`（例: `estimateItems`）と `snake_case`（例: `estimate_items`）が混在している |
| **発見経緯** | テストデータ生成時に `estimateItems` で保存したが、`detail.js` の `initEstimates()` は `data.estimate_items` を読む設計だったため、見積明細が空と判定された |
| **影響範囲** | Firestoreスキーマ全体。特に `cases` コレクションの `estimate_items` / `invoice_items` 周辺 |
| **発生頻度** | 新機能追加や外部連携時に、開発者が規約を誤る可能性あり |
| **優先度** | **低** |
| **推奨対応** | 命名規約ドキュメント（`docs/governance/NAMING_CONVENTION.md`）を作成し、Firestoreフィールドは `snake_case` に統一する方針を明文化。既存データのマイグレーションは段階的に実施 |
| **概算工数** | ドキュメント作成: 1時間 / マイグレーション: 影響範囲次第で8〜20時間 |
| **今回対応しなかった理由** | 影響範囲が広く、今すぐ事故になる類ではない。テスト側で正しいフィールド名を使用することで回避可能 |
